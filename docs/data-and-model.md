# Data and model pipeline

## Source and target

Taxi-Minute uses the [NYC Taxi and Limousine Commission's monthly yellow-taxi trip records](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page) and its [taxi-zone lookup table](https://d37ci6vzurychx.cloudfront.net/misc/taxi_zone_lookup.csv). TLC publishes the trip files as Parquet, typically with a two-month delay. TLC notes that the records come from authorized technology providers and does not guarantee their accuracy.

The label is elapsed minutes from `tpep_pickup_datetime` to `tpep_dropoff_datetime`. Model inputs available before a trip are `PULocationID`, `DOLocationID`, and pickup date and time. The website accepts addresses, map pins, or named taxi zones and a departure time in New York time. Metered distance, fare, and other after-trip fields are excluded.

## Where the data lives

The pipeline downloads the four selected monthly Parquet files and taxi-zone lookup CSV into `.data/` at the repository root. This directory is created on the first download and is ignored by Git. It is a local cache, so you can delete it and the next training run will download the files again. A plain `data/` directory is not used or tracked by this project.

GitHub Actions starts on a fresh runner, downloads the files it needs into its own temporary `.data/`, and discards that cache when the job ends. The repository stores the browser-ready model and metadata, not the raw trip records. See [`site/metadata.json`](../site/metadata.json) for the exact months and source-file hashes used by the current published model; those values update when a candidate is promoted.

## Address and map inputs

The browser uses [NYC Planning's GeoSearch](https://geosearch.planninglabs.nyc/docs/) for address suggestions and geocoding. Search requests are sent to that service; the trip prediction stays in the browser. Users can also place and drag pickup and drop-off pins without an address search. The site matches each coordinate to one of the [TLC's taxi-zone polygons](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page) using a local point-in-polygon lookup. [`site/zone-boundaries.json`](../site/zone-boundaries.json) is a compact WGS84 conversion of the TLC shapefile, built with [`scripts/build_zone_boundaries.py`](../scripts/build_zone_boundaries.py). Named zone selectors remain available if search or map services are unavailable.

The map uses [Leaflet](https://leafletjs.com/) with [OpenStreetMap tiles](https://operations.osmfoundation.org/policies/tiles/). These public services are best effort; the site relies on them for map and address interactions, while the model and manual zone selection are hosted with the site. The line drawn between two pins is a visual connection, not a calculated road route.

## Selection and training

1. Discover the latest four yellow-taxi Parquet months linked from the TLC page and download them to the Git-ignored `.data/` cache.
2. Keep rows whose pickup and drop-off zone IDs are 1–263, pickup timestamp belongs to the file's month, and calculated duration is 2–120 minutes. Take a deterministic 8% hash sample of those rows to fit the free GitHub Actions runner.
3. Train a LightGBM regression model on the first three months. Features include pickup and drop-off zones, calendar/time values, and historical route median and count. Each training month's route statistics come from the *other* training months so its own trip durations cannot leak into its route features.
4. Validate on the fourth, newest month. Route statistics for this month come only from the three training months.
5. Report mean, median, and 90th-percentile absolute error in minutes. Compare mean absolute error (MAE) with a historical route-median baseline and evaluate the currently published model on that same validation month.

A candidate must be within 3% of the route-median baseline's MAE and within 1% of the current model's MAE. If it fails, the published model stays in place. The latest measurements, row counts, months, source URLs, and file SHA-256 hashes are in [`site/metadata.json`](../site/metadata.json). These values are generated by the pipeline, so the metadata file is the source of truth after each update.

## Validation and release gates

The split is chronological: the first three selected months are used for training, and the newest month is held out for validation. This tests a later period than the training data. The update script reports MAE, median absolute error, and 90th-percentile absolute error for the candidate; MAE determines promotion. A candidate more than 3% worse than the route-median baseline fails the job. A candidate more than 1% worse than the current published model on the same validation month is not promoted. Passing the metric gates is followed by `npm test`, which checks browser inference against native LightGBM predictions before GitHub Actions commits and deploys the artifacts.

The model and validation metadata are versioned together in Git. The metadata stores the training and validation months, sample size, evaluation metrics, source URLs, and SHA-256 hashes of downloaded Parquet files. The lockfile pins Python dependencies, while the source hashes document exactly which downloaded files produced a release. The script does not currently verify those hashes on a later download or track experiments in a separate registry.

## What gets published

The pipeline writes a compact tree model to [`site/model.json`](../site/model.json), taxi-zone labels to [`site/zones.json`](../site/zones.json), and provenance and metrics to [`site/metadata.json`](../site/metadata.json). [`models/champion.txt`](../models/champion.txt) preserves the native LightGBM version for comparison on the next month. [`tests/parity_cases.json`](../tests/parity_cases.json) holds held-out predictions checked by `npm test` against the browser inference code. Raw trip files are never committed. The site reads these committed artifacts directly, so a deployed release does not need a running prediction server.

## Limitations

- The estimate uses taxi zones, not exact addresses, route choices, live traffic, weather, or events.
- Addresses in the same pickup and drop-off zones produce the same model features for the same departure time. Points outside the supported polygons cannot be used as pins; users can choose zones manually instead.
- The displayed rough range is built from the 80th percentile of absolute errors on one validation month. It is a global guide, not a calibrated interval for each route or a guarantee of coverage.
- A new TLC month arrives after a delay. Trip records may have inaccuracies, and changes in source schema or page links can cause the update workflow to fail until the parser is adjusted.
- The model is scoped to yellow-taxi trips with valid 2–120 minute recorded durations. Other services and trips outside that range are not represented in training or validation.
